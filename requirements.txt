# Runtime dependencies.
#
# Two dbt adapters on purpose, per ADR 0001: DuckDB is the canonical engine
# and BigQuery is the secondary one. Both are needed because model SQL must
# compile on both.

requests>=2.31
google-cloud-bigquery>=3.14
google-api-core>=2.11

# Upper bounds are load bearing. A bare ">=1.8" resolves to a dbt-core 2.0
# alpha whose build downloads a wheel from GitHub releases during metadata
# generation, which fails on any machine that cannot reach github.com and
# breaks `make setup` with an error that looks nothing like a version
# problem. Raise these deliberately, not accidentally.
dbt-core>=1.8,<2.0
dbt-bigquery>=1.8,<2.0
dbt-duckdb>=1.8,<2.0

# pyarrow writes the raw zone; duckdb reads it. Both are direct dependencies
# of ingestion/ now, not just of dbt-duckdb, so they are pinned here rather
# than inherited. See ingestion/raw_zone.py for why the two split that way.
pyarrow>=15.0
duckdb>=1.0

# H3, and the reason it is here rather than as a DuckDB extension. BigQuery
# has no H3 support of any kind, so an H3 call in a dbt model cannot compile
# on both targets, which ADR-1 requires of every model. ingestion/spatial.py
# computes the cells once in Python and both engines read the resulting
# BIGINTs. ADR-5 has the full argument.
#
# Major-version pinned because the v3 to v4 rename changed every function
# name in the library (geo_to_h3 became latlng_to_cell, and so on), so a
# major bump is a rewrite of spatial.py rather than an upgrade.
h3>=4.0,<5.0

# Object storage, for the Parquet zones in GCS and for `make publish` uploads
# (ADR-9). Two bounds, both load bearing and both discovered the hard way:
#
#   gcsfs<2026            2026.x requires google-cloud-storage>=3.11, and
#                         dbt-bigquery caps it below 3.2, so the newest gcsfs
#                         and this project's dbt adapter cannot coexist.
#                         Installing it anyway leaves an importable gcsfs that
#                         raises ModuleNotFoundError on
#                         google.cloud.storage.asyncio at first use.
#   google-cloud-storage  pinned explicitly rather than inherited from
#                         dbt-bigquery, because publish/export.py imports it
#                         directly and a transitive dependency that a dbt
#                         upgrade could drop is not a dependency.
#
# fsspec rather than DuckDB's httpfs is a decision, not a default: httpfs needs
# HMAC interoperability keys, which means a second credential. ADR-9 has the
# argument and the measurements.
gcsfs>=2025.5,<2026
google-cloud-storage>=2.14,<3.2

# PyYAML, because ingestion/dataset_registry.py reads the dataset registry out
# of dbt/dbt_project.yml (PLAN-5 step 4). dbt-core depends on it, so it was
# already in every environment that ran this project, and it is listed here for
# the same reason google-cloud-storage is: ingestion imports it directly now,
# and a transitive dependency that a dbt upgrade could drop is not a dependency.
# This is also what makes the ingest.yml runner, which installs this file and
# not requirements-dev.txt, able to read the registry at all.
pyyaml>=6.0

# numpy is already present transitively via pyarrow, and is pinned here
# because ingestion/geometry.py imports it directly for the vectorised
# point-in-polygon test. Point by point in pure Python that step took
# minutes; batched through numpy it takes seconds, which is the difference
# between exact boundary assignment being affordable and not.
numpy>=1.24
