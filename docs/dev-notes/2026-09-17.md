## Findings

**1. The 403 is a DataSF host migration, not a credentials problem, and the
09-12 note's follow-up sends the next session to the wrong place.** DataSF
moved the portal from `data.sfgov.org` to `data.sf.gov`. The old host is not a
working alias, and the way it fails is what made this look like an auth
failure. A bare `GET /resource/vw6y-z8j6.json?$limit=1` gets a normal 301 to
the new host. Add a `$select` and the same host returns **403 with an nginx
HTML body** and no redirect at all — and `$select=*,:id,:created_at,:updated_at`
is on every request `socrata_pages` makes. Bisected parameter by parameter:
`$where`, `$order`, `$limit` and `$offset` all still 301 cleanly; `$select`
alone is the trigger.

**2. The app token was never involved, and this is checkable in one command.**
The 403 reproduces from a cold shell with no token whatsoever, and the new host
returns 200 for the identical query with no token. So the empty
`SOCRATA_APP_TOKEN` in the failing job env is a true observation with no causal
connection to the failure — the repository secret may well also be unset, but
setting it would have fixed nothing. Checked across all six socrata datasets in
the registry with the full failing query shape:

| dataset | socrata_id | data.sfgov.org | data.sf.gov |
|---|---|---|---|
| `311_cases` | `vw6y-z8j6` | 403 | 200 |
| `building_permits` | `i98e-djp9` | 403 | 200 |
| `business_locations` | `g8m3-pdis` | 403 | 200 |
| `analysis_neighborhoods` | `ajp5-b2md` | 403 | 200 |
| `supervisor_districts` | `f2zs-jevy` | 403 | 200 |
| `film_locations` | `yitu-d5am` | 403 | 200 |

**3. `_check_app_token` was right to stay silent, and that is the gap.** Its
guard is `resp.status_code == 403 and "app_token" in resp.text`. The body here
is nginx's HTML error page, so the substring is absent and the function
correctly declined to blame the token. What the caller then saw was
`raise_for_status`'s bare 403 against a 300-character percent-encoded URL,
which is exactly the artefact that got read as an auth failure anyway. The
special case exists to stop a 403 being reported as a URL nobody can read; it
covers one cause of 403 and this was another.

**4. The retry loop spent 15 seconds proving a permanent failure three times.**
`_get_with_retries` treats every `RequestException` as transient. A 403 from an
edge proxy is not, which is why the job burned ~70s per run to die the same way
four days running. Not changed here; see Follow-ups.

**5. The watermark lines up with the migration to the day.** Re-running
`socrata_pages('vw6y-z8j6', '2026-09-08T10:25:36.237Z', '')` — the exact
watermark from the failing log — now returns a full 5000-row page whose first
row is `:updated_at = 2026-09-09T10:19:09.785Z`. The last successful run was
09-08 and the first failure 09-09, so nothing was lost: the delta resumes from
where it stopped and the nine missed days are still upstream.

## Follow-ups

- **`_get_with_retries` should not retry a 403.** Finding 4. It is a small
  change with a real payoff — a permanent failure would report in 1s instead of
  70s — but it is a judgement call about which statuses are terminal (401, 403,
  404 yes; 429 and 5xx no) and it deserves its own change rather than riding
  along with a hostname.
- **`_check_app_token` could widen to cover any 403.** Finding 3. Today a 403
  that is not about the token produces a bare `HTTPError` against an unreadable
  URL. Something that says "403 from <host>; this is the Socrata host, the
  token is/is not set, the response body was HTML not JSON" would have cut this
  diagnosis to one read. Related to the item above and probably the same change.
- **Confirm the 09-18 09:17 UTC cron goes green**, which is the only real
  proof this is fixed. Note that PLAN-10 step 5 is *not* waiting on it: the
  09-12 note made the dead ingest the gate on step 5, but ADR-20 was refused on
  09-13 and step 5 is now marked skipped, because there is no snapshot left to
  verify. What actually remains in PLAN-10 is step 7 (the materialization
  measurement, which the plan says a stale zone does not block) and step 8's
  leftovers.
- **Set the `SOCRATA_APP_TOKEN` repository secret** for rate limits, on its own
  and without the expectation that it fixes anything.
- Whoever next regenerates the context pack should sweep the remaining
  `data.sfgov.org` strings listed under Not done in the same pass.

### Correction to the first session, above

That session's "Not done" says changing `tools/context_pack/pack_inputs.py`
"turns one red CI job into a different red CI job" because the committed packs
are drift-checked. **That is wrong, and the truth is worse.** `check_pack`
compares exactly four things — target name, prose revision, spec version and
the per-model schema hash — and `generate.py:579` and the CI comment both say
so. Source URLs and the licence line are in the pack's `identity` block and are
compared by nothing. So changing the generator would not have gone red. It
would have gone *green*, with the generator and the committed artifact
disagreeing silently until whoever next ran `make context-pack` got an
unexplained diff in a pull request about something else. The first session
declined to make the change for a reason that did not exist, and the hazard it
should have named is the opposite one.

### Findings

**1. The drift check does not compare the pack's identity block.** See the
Correction. Worth stating separately because it generalises: `check_pack`'s four
comparisons are all about *shape*, and everything in the pack that is *content*
— licence, source URLs, publisher, prose that is not revision-stamped — can
drift from its generator without CI noticing. The two equality tests added here
cover the two known cases. Anyone adding a third derived field to `identity`
should add a third test, because the gate will not do it for them.

**2. A guard that forbids naming the dead host deletes its own explanation.**
The first version grepped for the bare string and immediately failed on the
comment above `SOCRATA_DOMAIN` — the one that explains why the constant is what
it is. Rewriting that comment to satisfy the test would have removed the only
in-code record of the outage in order to keep a test about the outage green.
The guard now matches `//data.sfgov.org` and `(data.sfgov.org)`, which are the
two shapes a URL actually takes, and prose may name the host freely. Not a
weaker test: a bare mention in a comment cannot produce a 403.

**3. The fixtures contain `mobile311.sfgov.org` and must keep it.** Photo links
in `tests/fixtures/socrata/311_cases.json` are captured API values, not
requests this repo makes. A tree-wide find-and-replace would have falsified the
fixture. The guard's search paths exclude the fixture data, and
`docs/dev-notes/` and `docs/decisions/`, which are immutable history under
CLAUDE.md's working agreement and name the old host because it is what
happened.

**4. The terminal-status change turns 70 seconds into 0.8.** Measured by
replaying the outage: point `SOCRATA_DOMAIN` back at the retired host and call
`socrata_pages` with the watermark from the failing log. Before, three attempts
and 15s of backoff ending in a bare `HTTPError`. Now one attempt, 0.8s, and:

> `403 from https://data.sfgov.org and retrying will not help. Token sent: no.
> The body is not JSON, so this was refused in front of the API rather than by
> it -- a proxy, a WAF, or a host that no longer serves this dataset. Check
> that SOCRATA_DOMAIN is still where DataSF publishes: '<html>...403
> Forbidden...nginx'`

"Token sent: no" is the clause that would have prevented the 09-12 note's wrong
conclusion, and it costs one dict lookup.

**5. The context pack was considered for retirement and kept.** The question
raised was whether disabling it would simplify things. It would not: it was
four string literals in an artifact that is otherwise doing its job, the schema
hashes it compares catch a real class of defect, and a *disabled* pack is a
committed artifact that rots silently, which is strictly worse than the
divergence finding 1 describes. Recorded so the next person asking does not
have to re-derive it.
