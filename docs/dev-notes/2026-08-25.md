## Findings

**The gap list is the part worth keeping.** Six decisions have no mechanism
behind them, and they were found by looking for the check rather than by
assuming it:

- No linter, test or CI step forbids a geometry function or an H3 call in a
  model. `dbt compile --target bigquery` renders either happily, so a
  DuckDB-only `h3_latlng_to_cell` would pass `make check` and fail only under
  `make build-bigquery`, which is not in CI. ADR-5 and ADR-6 both rest on this
  and both are held by review.
- Nothing covers `RAW_ZONE_DIR` beating `RAW_ZONE_URI`. PLAN-4's Done-when
  records it was asserted by hand in a shell with both set; there is no test.
  Reversing that precedence would make `set -a; source .env` silently change
  what the CI gate tests, which is ADR-9's stated reason for the rule.
- Nothing prevents `--apply` being added to a workflow file. It is refused in
  ADR-14, ADR-17 and ADR-18 section 5, and the only mechanism is review.
- ADR-8's manifest-last ordering has no test. It was verified once by hand
  under PLAN-4 step 9. `--prune` refusing a destination with no prefix
  (`publish/export.py:298`) is a different guarantee.
- ADR-12's partitioned export branch (`publish/export.py:214`) is unexercised,
  including in CI, which ADR-12 records as a real cost.
- The scope deletion of ADR-16 and ADR-18 exception 3 is caught only by
  `check_runs.py`'s warning, which is a warning and not a failure.

**`make check` is not quite everything CI runs.** `Makefile:457` is
`test-python lint leak-check compile-bigquery ci-build`, and `ci-build`
(`Makefile:438`) does not invoke `generate.py --check`. The two context-pack
drift checks live only in `.github/workflows/ci.yml:200` and `:228`, so a pull
request can be green locally and red in CI on a moved schema hash. `CLAUDE.md`
describes the target as "everything CI runs on a PR"; that is the intent and
the mechanical difference is now footnoted in `orientation.md`.

**"Three of which compilation cannot catch" is ambiguous and the ambiguity
matters.** `CLAUDE.md` says the first BigQuery build found four cross-engine
defects, "three of which `dbt compile --target bigquery` cannot catch because
compiling never asks the warehouse whether a type exists". That reads as
implying the fourth is compile-catchable. It is not. PLAN-4 step 3 and PLAN-1's
Done-when both split it as "three of the four defects were type errors that
only executing could find", so the three counts type errors and not uncatchable
defects. The fourth, `x_safe_int` rounding on BigQuery and truncating on
DuckDB, is uncatchable for a stronger reason: nothing is statically wrong, both
engines execute the SQL, and they return different numbers. Recorded as a
footnote rather than a correction, since `CLAUDE.md` wins and its count is
right.

**Four places where an `active` document has been overtaken.** None is a
disagreement about a decision and all four are in immutable text, so all four
are footnotes:

- ADR-1 says attaching billing removes the sandbox expiry. PLAN-4 step 1 found
  it does not: `raw_datasf` carried `default_table_expiration_ms` as a dataset
  property that outlived the sandbox and had to be cleared by hand.
  `CLAUDE.md`'s trap list carries the residue.
- ADR-6 says boundary sets are a closed list in `datasets.py`. That file became
  `dataset_registry.py` under PLAN-5 step 7 and the list itself moved into
  `vars.pipeline_sources` under PLAN-5 step 4. The claim holds; the filename
  does not.
- ADR-9 says "writes stay local for now" and points at PLAN-4 step 6. That step
  closed on 2026-08-01.
- ADR-13 says "Two of the three packs do not exist yet. Only `duckdb` is
  generated." PLAN-8 landed the published pack the same day ADR-13 was
  accepted, and ADR-15 struck the third. `CLAUDE.md` says two, and two is the
  intended number.

**One stale code comment, which is the class PLAN-5 step 13 was sweeping for.**
`dbt/models/staging/spatial/stg_spatial__point_geography.sql:8` says the model
carries "H3 cells at three resolutions". It carries two. PLAN-5 step 13 removed
the same sentence from `_spatial__sources.yml` and missed this one. Not fixed
here, because this session was scoped to write a document and not to edit
models; it is a one-word change for whoever is next in that file.

## Follow-ups

- **Decide what kind of document `orientation.md` is.** `docs/README.md` says
  everything in `docs/` is one of five kinds and this is a sixth: a derived
  reader-facing layer that restates decisions without being one. Either add a
  row to that table with a mutability rule, or fold the document somewhere that
  already has one. It needs a rule about when it is regenerated, because it
  will rot the same way the pack would without its drift check, and unlike the
  pack nothing checks it.
- **Fix the three-resolutions comment** in
  `dbt/models/staging/spatial/stg_spatial__point_geography.sql:8`.
- **Run the prune's acceptance test in its clean form.** ADR-18 section 8 asks
  for it at the next apply, before the 09:17 UTC ingest, and records that it has
  not been run clean since 2026-08-07.
- **Consider whether `make check` should run the two pack drift checks.** The
  argument against is that `ci-build` is fixture-scoped and fast and the pack
  check needs the committed artifact rather than the fixture one; the argument
  for is that the local gate claims to be the CI gate. Either is defensible and
  the current state is that the claim is slightly wider than the target.
