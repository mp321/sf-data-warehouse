## Findings

Three decisions, ranked by how likely they are to hurt in a year.

1. **A run's network cost followed the size of the whole raw zone, about
   three times over.** Fixed here. ADR-22's context blamed three whole-table
   reads; the cause was one level down. gcsfs pads every read to 5 MiB, the
   raw files are about 8 MB, so asking for one column downloaded most of each
   file. Measured through the real functions on a 366 MB local copy of the
   zone (311 copied into 12 partitions), behind a fake bucket with gcsfs's
   read defaults:

   | Step | Before | After |
   |---|---|---|
   | `ingest.py` watermark, delta datasets | 190.5 MB | 0.8 MB |
   | `spatial.py` `raw_input_state` | 593.0 MB | 26.0 MB |
   | `spatial.py` `read_points`, 311 | 198.4 MB | 31.1 MB |
   | `spatial.py` `read_points`, business | 53.1 MB | 10.8 MB |
   | Total | 1035.1 MB, 2.83x the zone | 68.7 MB, 0.19x |
   | Requests | 483 | 575 |

   The before figure matches the "about 3x" measured on the bucket on
   2026-10-01. Answers are identical. A full-table load is unchanged: 258 MB
   and 96 requests either way, because DuckDB already reads whole files in
   two requests.
2. **Delta history keeps every row upstream re-sends, with no bound.** Open.
   907 MB of 311 against a 5 GB free tier, about 110 days of daily runs. This
   is ADR-22, and it is the owner's decision because it deletes from a delta
   table.
3. **Dependencies are floors, not pins, and CI runs only on a push.**
   `duckdb>=1.0`, `pyarrow>=15.0`, `numpy>=1.24` and `requests>=2.31` have no
   ceiling and there is no lockfile. The README's first claim is that a fresh
   clone builds; on a paused repo nothing will say when that stops being true.
   The local venv is Python 3.14 with duckdb 1.5.5 and pyarrow 25; CI uses
   Python 3.11. Neither set is recorded.

Also seen, not ranked: `socrata_pages` pages by `$offset`. A row updated
during a fetch moves to the end of the ordering, every later row shifts down
one, and the next page skips a row that no later run asks for. Not observed:
whether the two runs that wrote exactly 5,000 rows (10-02, 10-05) are this is
not investigated. A cursor on `(:updated_at, :id)` would close it and needs a
check against the live API first.

Smaller:

- The tour page said 21 decision records; there are 22.
- `build.py` reproduces the committed page byte for byte apart from that
  count, so the page can be rebuilt, not edited in place.
