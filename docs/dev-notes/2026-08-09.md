## What the bucket had done on its own, which is the finding the session turned on

**So the cost ADR-14 named arrived in two days rather than in the abstract.**
That ADR wrote down "the zone is now bounded by someone remembering" and set its
own revisit trigger at "when the zone is bounded by something other than someone
remembering". Nobody remembered. The neglected growth rate comes out at 54.6

allowance, which recomputes to 86. The estimate was accurate and the thing it
was an estimate of was in progress.

## ADR-16: a cut dataset is a scope deletion, and the prune is not the tool

PLAN-9 said the prune was the wrong tool and gave the reason as missing inputs:
no `refresh`, no `grain_key`, because neither dataset is in the registry. That
is true and it understates the case, and the stronger version is what made this
an ADR rather than the dev-note line the plan offered as an alternative.

**The proof is not unavailable, it is false.** `prune_raw.py` deletes a
partition when a surviving later one holds every `grain_key` at values no older.
A dataset leaving the project has no surviving partition, so every key is
unreachable afterwards, which is the exact condition ADR-14 makes the tool
refuse on. Teaching it this case means teaching it that its central check does
not apply, and a destructive tool with a flag that switches off its proof is
worse than one without the flag.

What replaces it is a repo proof rather than a data proof, and it is the
stronger of the two: the registry has one copy, `test_dataset_registry.py`
asserts in both directions that it agrees with the dbt sources, the staging
models and the fixtures, and dbt cannot read a table that is not a declared
source. Neither is one. The prune's proof has to be re-established per candidate
because the zone moves under it; this one is a property of the repository that
CI checks on every PR.

**Two tools had been saying so for five days.** `check_runs.py` warned on every
run, "raw_city_budget is in the zone and not in the registry, so nothing reads
it", and `prune_raw.py` refused the name outright with `unknown dataset(s)`. The
gap was never detection. That is why ADR-16's revisit clause makes that warning
load bearing and why it now names the ADR: a warning that fires forever with
nobody acting on it becomes furniture, which is what happened here.

Deleted with `gcloud storage rm --recursive` on the two prefixes. 55,465,016
bytes and 42 objects, enumerated from a full listing first and checked to be
zero objects outside the two prefixes before anything ran. Raw prefix
323,379,850 to 267,914,834 bytes, 216 objects to 174.

## ADR-17: the proof runs weekly and the deletion still does not

ADR-14 answered "where does the prune run" as one question. It is two, because
`prune_raw.py` does two things and only one is destructive: a read-only proof
over two columns of two partitions, and `--apply`. Scheduling the first is not a
smaller version of scheduling the second, it is the thing that gets the second
run.

**Every word of ADR-14's case against a cron that deletes data was re-read and
kept**, and the two days of evidence strengthen rather than weaken it: what they
show is that nobody was watching, which is the worst condition under which to
have a scheduled job deleting things. `--apply` appears nowhere in the new
workflow and the ADR says it must be reopened by an ADR rather than by a line
added to a YAML file.

`.github/workflows/retention.yml`, Mondays 11:29 UTC, runs
`prune_raw.py --max-bytes 1000000000`. New in the tool: `--max-bytes` weighs the
whole zone, prints it against the threshold and against what an apply of the
plan it just reported would leave, and exits 4 if over. Off unless given,
because a threshold is a property of one bucket's allowance and not of the tool.

**The threshold is 1 GB and the number is chosen so a breach means one thing.**
With the prune running the zone sits near a 170 MB floor, set by the keep window
of two partitions of the largest snapshot dataset, and grows at the delta rate
of 4.86 MB/day, so delta growth alone needs over 170 days to reach 1 GB. Without
the prune, snapshot churn reaches it in about 15. It therefore cannot fire
because the project grew; it fires because the apply stopped being run. About 70
days of runway remain to the allowance at the neglected rate, which is three
more Mondays.

**Exit 3 outranks exit 4 when both hold**, and that ordering is the part worth
keeping. Over budget asks the reader to prune. Unproven says a snapshot dataset
failed its proof, which ADR-14 answers with "stop pruning until it is
understood". Returning the cheaper verdict as the headline would invite exactly
the action the more serious one forbids. There is a test for the precedence
rather than only for each code.

Weekly rather than daily: the proof is about 34 seconds against the bucket, and
daily would put a job that can go red in front of a human six times more often
than it has anything new to say. A check that cries wolf is the failure this
whole design avoids.

## Findings

**`raw_ingest_runs` is built by globbing the zone, not by reading the registry.**
`load.py`'s `_load_runs_duckdb` reads `*/_runs/*.json` across every prefix, so
the two cut datasets had been contributing 22 run manifests to that table since
they were cut. The deletion took it from 136 rows to 114. This was checked
before deleting rather than discovered after, because it is the one path by
which a dataset nothing declares as a source can still reach the warehouse.

It changes no model. `mart_pipeline_freshness` reads that table but its grain is
one row per *registered* source and it builds its rows from
`var('pipeline_sources')`, so a `city_budget` run could only ever have joined to
nothing. Confirmed after the fact: 7 rows, and 19 models built.

**`docs/README.md` still listed PLAN-8 as active.** Its own file has
`status: done` and the 2026-08-07 fourth session closed it, but the index table
was not updated in the same pass. Fixed here with the closing summary. Worth
noting because that table is what `docs/README.md` tells a new session to read
first, so it is the one place where being a day stale costs the most.

**A rebuild was the acceptance test and it needed a different argument from the
prune's.** ADR-14's test is "prune, rebuild, no row count moves", and it earns
its keep because a prune deletes rows that staging is supposed to be
deduplicating away, so a moved count would falsify the premise. Here the
equivalent claim is structural and cheaper: `load.py` iterates
`list(DATASETS)`, and no model can reference a table that is not a declared dbt
source. The rebuild was run anyway and came back `PASS=172 ERROR=0`, which
confirms the pipeline is green rather than proving anything the structure did
not already.

## `dbt/target/manifest.json` is the bucket build's, not the fixture build's

The note above says the opposite and the check it recommends is the one that
disproves it.

- Committed pack: `invocation_id` `c0e3245a-5fb9-4e20-a081-21a7058289d0`,
  `generated_at` 2026-08-08T03:09:56Z, carried in both `build` and

- Working manifest: `invocation_id` `db0012e8-2d83-47ae-ac38-5f2b371c59d8`,
  `generated_at` 2026-08-09T19:05:44Z.

They differ, which is what the note predicted. **The part the note gets wrong is

first and the bucket rebuild ran last.

The practical consequence is unchanged and slightly sharper: **regenerating a
pack right now would describe the bucket build**, which is PLAN-9 step 5's
