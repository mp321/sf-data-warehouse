# 2026-09-13

carries a 2026-09-12 timestamp because that is when it was taken; the session
closed on the 13th. Steps 1 and 2 are in `docs/dev-notes/2026-09-12.md` and the

## Scope

PLAN-10 step 3, which is ADR-19 step 4: one shared macro restricting every
`refresh: snapshot` staging model to the `grain_key`s present in the newest
`ingest_date`, and the one-time row-count movement captured per model against

## Changes

`dbt/macros/newest_snapshot.sql` (new) — `restrict_to_newest_snapshot`, taking
the CTE to filter, the registry's `grain_key`, and the `source()` relation. The
last two arguments are both performance decisions and the docstring carries the
measurements; see finding 2.

`dbt/tests/assert_snapshot_staging_holds_only_the_newest_partition.sql` (new) —
one singular test driven off `vars.pipeline_sources`, so it covers a sixth
snapshot dataset the day it is registered. Compares each snapshot staging
model's row count against the distinct `grain_key` count of its source's newest
partition. Counts rather than sets, and the header argues why that is
sufficient here rather than leaving it to be assumed.

Five staging models — `stg_datasf__business_locations`,
`stg_datasf__film_locations`, `stg_datasf__analysis_neighborhoods`,
`stg_datasf__supervisor_districts`, `stg_census__block_groups` — each gains a
`current_snapshot` CTE between `deduplicated` and `renamed`. Four of the five
are no-ops today and are commented as such, because a rule applied only where
it currently bites is a rule that silently stops being applied.

## Findings

**1. The plan predicted one model would move. Three did, and this is exactly
what step 1 exists for.** PLAN-10 step 3 says "Expected: only
`stg_datasf__business_locations` moves, by 27." The staging model did move by
27, and so did `int_point_activity` (-27) and `mart_activity_by_h3` (-1). The
prediction was not wrong about the cause, it was under-specified about the
consequence: the 27 withdrawn registrations are point events, so they leave the
activity union with staging, and one h3 cell / dataset / category / month group
had no other row and disappeared entirely. `mart_activity_by_neighborhood` did
**not** move, because every group it would have touched still has other rows.
Without the baseline none of this would have been distinguishable from the
macro filtering more than it should.

**2. The obvious way to write the macro cost an 18x build, and the fixed
version is faster than having no macro at all.** Summed dbt node execution
time on the bucket zone, from `meta_dbt_run_results`:

| | nodes | node time |
|---|---|---|
| before this step | 168 | 116.7s |
| macro, first form | 169 | **2082.0s** |
| macro, as landed | 169 | **92.4s** |

Two independent causes, and neither is the semi-join being expensive:

  - **Naming the `source` CTE in all three places.** The first form read
    `select * from source where grain_key in (select grain_key from source
    where ingest_date = (select max(ingest_date) from source))`. A CTE
    referenced three times stops being a candidate for projection pushdown, so
    DuckDB materialises it once at full width: about forty columns of 8,414,422
    rows. Pointing the two subqueries at the `source()` relation instead lets
    each read the two columns it needs. That one change is 9.08s to 1.51s on
    the view.
  - **Filtering before the dedup rather than after.** The predicate is on the
    grain key and the dedup keeps exactly one row per grain key, so the two
    commute, and applying the semi-join to 366k rows instead of 8.4M is the
    rest of the gap. 1.51s to 0.74s, against 1.09s for the model as it was
    before this step.

The `max()` must still come from the relation and not from `deduplicated`, and
that is not a performance point: a key whose newest `_socrata_updated_at` lives
in an older partition survives the dedup carrying that older `ingest_date`, so
the newest partition's date is not guaranteed to appear in the deduplicated set
at all.

**3. Views amplify, which is why a 7-second view cost seven minutes of build.**
Staging models are views and `int_point_activity` is a view over them, so
nothing is computed once. `stg_datasf__business_locations` alone has fifteen
direct children in the manifest: three models and twelve tests. Every one
re-evaluates the whole chain. A cost measured in isolation on a staging view
should be multiplied by its child count before deciding it is acceptable.

**4. ADR-19's Decision section and its Option D rationale ask for two different
things, and only one of them is a decision.** The Decision says "restricting
snapshot staging models to the `grain_key`s present in the newest
`ingest_date`", which is what landed. Option D and the fourth revisit clause
both describe step 4 as making "an older partition genuinely unreachable",
which is the stronger rule of reading only the newest partition. They return
identical rows on this zone and always have, because the difference shows only
when a surviving key is fresher in an older partition, which is the prune's
second limb, measured 0 on every partition of every dataset to date. **They
differ in what a later decision may rest on.** With the rule as landed, older
partitions are still read for values and are therefore not unreachable, so the
deferred question of whether `prune_raw.py` may treat them as deletable does
not follow from this change alone. ADR-19 declines that decision explicitly and
asks for its own acceptance test, and this session declined it the same way
rather than taking it by implementation. The macro's docstring says so in the
place someone would be standing when it mattered.

**5. `ingest_date` really is queryable on BigQuery, checked rather than
trusted.** ADR-19 asserts it and the whole macro rests on it, so it was
verified in `load.py` before a line was written: external tables get hive
partitioning in `STRINGS` mode, deliberately so BigQuery does not infer DATE
from `ingest_date=2026-07-31`, and the explicit column list includes it. It
sorts lexically because it is ISO-8601, which is what makes `max()` the newest
partition rather than the last one alphabetically.

**6. The acceptance test is red on real data and green on fixtures, and that is
the honest shape of it.** It failed before the change with exactly one row,
`business_locations 366509 366482 27`, and passes after on both engines. On the
local zone and the CI fixture zone it passes either way, because those hold one
partition per dataset and there is nothing for a withdrawal to be absent from.
So `make check` could never have caught this and cannot regress-test it; the
bucket zone is the only place the test has teeth. Recorded because a green CI
badge will now claim this is verified when what CI verified is that the SQL
parses.
